# Backend Django
Use uv for Python project management, dependency resolution, virtual environments, lockfile management, installation, and command execution. Keep `uv.lock` committed and use uv consistently in local development, Docker, documentation, and CI. Put production/runtime dependencies in `[project].dependencies`. Split development tooling into uv groups by concern: `lint` for Ruff, `typecheck` for Pyright, and `test` for pytest/pytest-django. Define `dev` as the aggregate group including `lint`, `typecheck`, and `test`. Add future tools to the narrowest meaningful group and introduce another group only for a distinct concern. Production installations must omit development groups.

Use Django + Django Ninja and follow the project's pragmatic hexagonal/vertical-slice architecture. Use repositories and query modules only where they create meaningful boundaries. Document Python using numpydoc in English, follow the project's mandatory blank-line separation rules, and enforce Ruff, Pyright, pytest/pytest-django on project-authored code, excluding Django-generated `**/migrations/**` from Ruff and Pyright, idempotent Celery jobs, explicit Ninja schemas, and thin routers. Keep provider payloads outside domain and public API contracts. Keep all backend tests in the top-level `tests/` directory beside `manage.py`, organized by test level/domain rather than colocated inside functional Django apps.

Treat Django migrations as generated artifacts: keep them committed and review schema operations, dependencies, reversibility, and deployment safety, but do not manually reformat or type-check them as project-authored code.

Numpydoc types use the specification's prose form, `list of str` and `int or tuple of int` rather than `list[str]`, in every section that carries a type: `Parameters`, `Returns`, `Yields`, `Receives`, `Other Parameters`, and `Attributes`. A class documents its non-method attributes in an `Attributes` section, including dataclass fields, `Protocol` members, and enum members with their serialized value; and lists every public method it defines in a `Methods` section as a full signature including the return type, such as `load(module_name, **environment_variables) -> ModuleType`, which is stricter than numpydoc on purpose because a growth threshold is not evaluable and a truncated signature is arbitrary; parameters are not annotated there and private methods stay out. Sections must also carry information: name the element type inside a container rather than writing `list of tuple` or a bare `dict`, omit `Returns` and `Yields` whose value is `None`, and never delete the `...` body of a `Protocol` method, which Pyright requires when the return annotation is not `None`.

Four style rules are non-negotiable; `.omp/AGENTS.md` holds the detail. Never open a project-authored Python file with a comment or module docstring, so the first meaningful line is an import or a declaration, while declaration-attached numpydoc stays mandatory. A `#!` shebang is exempt only on a genuinely executable script, and `manage.py` no longer has one. Document every test with exactly three lines, `GIVEN ...`, `WHEN ...`, `THEN ...`, and nothing else, while fixtures, factories, and helpers in `tests/` keep ordinary numpydoc. Separate every multi-line statement or expression from the statement above and below it with a blank line, except when it opens or closes its block or the formatter forbids it. Follow every statement that binds a newly constructed object or value with a blank line unless the next statement is another such binding; consecutive bindings such as runs of Django settings constants may stay adjacent, and so may method calls, attribute mutations, and registrations against an already-bound object, which is why a `Celery` app declaration takes a blank line before its `config_from_object` and `autodiscover_tasks` calls while those two calls stay together.
