# Frontend Next.js
Use Bun as the frontend package manager, dependency installer, runtime tooling, lockfile manager, and script runner. Keep `bun.lock` committed and use Bun commands in local development, Docker, documentation, and CI rather than npm, Yarn, or pnpm equivalents. Keep packages required by the built/running application in `dependencies`, and development-only formatting, type, test, and tooling packages in `devDependencies`. Classify dependencies by production runtime necessity rather than convenience.

Prefer Server Components and server-only feature data modules using native `fetch`, Next.js caching, and revalidation. Use Client Components only for browser interactivity and Zustand only for justified shared UI state. Keep feature code colocated by business domain and consume normalized product contracts rather than Sportmonks payloads. Document exported and reusable TypeScript APIs with TSDoc when documentation adds value. Format project-authored frontend code with Prettier, Tailwind canonical sorting, and deterministic import sorting. Exclude `src/components/ui/**` from Prettier formatting/checks because shadcn/ui primitives are treated as generated/vendor-like source unless the project intentionally takes ownership of a component. Separate every multi-line TypeScript statement or expression from the statement above and below it with a blank line, and follow every `const`, `let`, or `var` binding with a blank line unless the next statement is another binding; both halves of the blank-line policy are mandatory, not preferences. Use Vitest as the test runner and React Testing Library for component behavior tests. Keep tests under `src/tests/`, organized by level/domain; do not colocate test/spec files with functional source modules.

After modifying React or Next.js application code, run React Doctor against the changed scope before considering the task complete. Keep React Doctor in `devDependencies`, use the project-pinned version resolved through `bun.lock`, and never rely on `@latest` in CI. Treat findings as engineering signals: fix material correctness, performance, accessibility, security, or maintainability issues, but do not introduce unnecessary abstractions solely to satisfy the tool.

Every component, page, and layout that takes props declares a named props interface and documents each prop with a TSDoc comment on its own member. Never use an anonymous inline props type, whose members cannot be documented, and never use `@param` for props: TSDoc requires a parameter name and a destructured object has none, so dot syntax remains an open proposal. Export a props interface only when another module consumes it.

Four style rules are non-negotiable; `.omp/AGENTS.md` holds the detail. Never open a project-authored TypeScript file with a banner comment, so the first meaningful line is an import or a declaration; a TSDoc block attached to the first declaration is documentation, not a header, and triple-slash directives are exempt. Document every test with exactly three lines, `GIVEN ...`, `WHEN ...`, `THEN ...`, and nothing else, while helpers, factories, and stubs in `src/tests/` keep ordinary TSDoc. Follow every `const`, `let`, or `var` binding of a newly constructed object or value, including `new Foo()` and factory calls, with a blank line unless the next statement is another such binding; consecutive bindings may stay adjacent, and so may method calls, property mutations, and registrations against an already-bound object. Generated/vendored `src/components/ui/**` and `next-env.d.ts` are out of scope for the file-header rule.
