# Sticky Project Rules

- Current MVP scope is fixture discovery/detail, football statistics, bookmaker odds, and Sportmonks predictions/markets for the five subscribed leagues.
- Do not implement live ingestion, WebSockets, AI insights, custom ML models, or distributed microservices unless scope is explicitly expanded.
- Use Django Ninja for the REST API.
- Bun is the frontend package manager and runtime/tooling standard. Use Bun for dependency installation, lockfile management, and frontend scripts; do not introduce npm, Yarn, or pnpm workflows without an explicit project-wide decision.
- Frontend dependency classification is mandatory: runtime packages go in `dependencies`; development-only formatting, typing, testing, and tooling packages go in `devDependencies`.
- Use uv is the Python project and dependency management standard. Use uv for dependency resolution, lockfile management, virtual environments, package installation, and Python command execution.
- Backend dependency classification is mandatory: production/runtime packages go in `[project].dependencies`; development tooling uses uv `[dependency-groups]` named `lint`, `typecheck`, and `test`, with `dev` as an aggregate group including those focused groups.
- Put Ruff in `lint`, Pyright in `typecheck`, and pytest/pytest-django in `test`. Add future tools to the narrowest meaningful group; add a new group such as `docs` only for a genuinely distinct concern. Local development may use aggregate `dev`; CI should install only the focused group(s) each job requires when practical. Production backend installations/images must not install development groups.
- All engineering code, paths, filenames, identifiers, tests, migrations, Docker/CI configuration, technical documentation, logs, Git metadata, issues, PRs, and developer-facing names are in English.
- Markdown bullet items that are sentences or instructions must begin with an uppercase letter. If an official technology or package name begins with lowercase text, rephrase the bullet so the sentence still begins with an uppercase word.
- Python documentation follows numpydoc: `https://numpydoc.readthedocs.io/en/latest/format.html`.
- Start every Python docstring on the line after the opening `"""`, with nothing sharing that line. This covers every docstring in the backend, not only tests: classes, functions, methods, and one-line docstrings alike, so a one-line docstring occupies three lines. It departs deliberately from the numpydoc habit of opening with the summary, and Ruff is configured to match by ignoring `D200` and `D202` project-wide. TSDoc already opens with a bare `/**`, so the frontend satisfies the same shape by construction.
- Write numpydoc types in the prose form the specification uses, `list of str` and `int or tuple of int`, not the annotation form `list[str]`. This applies wherever a type appears, not only to return values: `Parameters`, `Returns`, `Yields`, `Receives`, `Other Parameters`, and `Attributes`. The specification anchors the notation in `Parameters` and defines the other sections as formatted like it, so the same form propagates to all of them. `Raises` and `Warns` name exception classes, where the question does not arise.
- Name the element type inside a documented container, never the bare container. Write `list of CapturedRecord` or `dict of str to Any`, not `list of tuple` or `dict`. When the module already declares a type alias for the shape, use the alias so the docstring and the annotation cannot drift apart.
- Omit a numpydoc `Returns` or `Yields` section whose value is `None`. A context manager that yields nothing and a callable annotated `-> None` have no value to describe, so the section would only restate the annotation; explain what entering or calling it does in the summary instead.
- Document a class's non-method attributes in an `Attributes` section, placed below `Parameters` when both exist. This covers annotated fields, dataclass fields, `Protocol` members, and enum members, and for an enum the serialized value is the information worth stating because it is the wire contract. Every backend class that has attributes carries this section.
- Document every method a class defines in a `Methods` section, placed after `Attributes`, as a signature followed by a one-line description on the next line, indented. The signature is the method name, its parameters as bare names without `self` and with a default where one exists, and the return type in annotation syntax: `load(module_name, **environment_variables) -> ModuleType`, `emit(record) -> None`. Do not annotate the parameters there; the `Parameters` section of the method's own docstring owns their types, and repeating them would duplicate it. Two deliberate deviations from numpydoc: the specification calls the section unnecessary and reserves it for classes with a wide method surface, and its examples stop before the return type. A threshold nobody can evaluate is worse than a rule that always applies, and truncating a signature before its return is arbitrary when the parameters are already written in Python syntax. Private methods stay out, which the specification forbids listing, and keep their own docstring. A class that defines no method, such as an enum or a Ninja `Schema`, carries no section.
- Keep the `...` body in a `Protocol` method after its docstring. It is not dead code: Pyright reports `Function with declared return type "X" must return value on all code paths` when a method whose annotation is not `None` has only a docstring for a body.
- Give every component, page, and layout that takes props a named props interface, never an anonymous inline type such as `Readonly<{ children: React.ReactNode }>`. Members of an inline type cannot carry a doc comment, so the props become undocumentable by construction.
- Document each prop with a TSDoc comment on its own interface member, and do not use `@param` for them. TSDoc's `@param` takes a parameter name, a destructured props object has none, and the dot syntax `@param props.health` is only the open RFC #19 rather than part of the standard. The member comment is also what an editor surfaces at the call site, on the JSX attribute.
- Export a props interface only when another module consumes it. A reusable component exports its props; a route-level page or layout keeps them local, since nothing outside the route can pass them.
- Keep `frontend/next-env.d.ts` untracked. Next rewrites it depending on which command ran last, `next dev` pointing at `./.next/dev/types/...` and `next typegen` or `next build` at `./.next/types/...`, so any tracked variant guarantees a permanently dirty tree for somebody. Every Next command regenerates it, and `bun run typecheck` runs `next typegen` first, so a fresh clone never needs a committed copy.
- Never begin a project-authored Python or TypeScript file with a comment or docstring that is not attached to a declaration; the first meaningful line of a file is code, an import or a declaration. Module-level docstrings and file-banner comments, single-line or multi-line, are prohibited, while documentation attached to a declaration stays mandatory even when that declaration is the first thing in the file. Functional directives are exempt: a `#!` shebang on a genuinely executable script and TypeScript triple-slash references such as `/// <reference types="next" />`. No project file carries a shebang today, because `backend/manage.py` is always run as `uv run python manage.py`. Generated/vendored `**/migrations/**`, `frontend/src/components/ui/**`, and `frontend/next-env.d.ts` are out of scope. Empty `__init__.py` package markers are fine; a package docstring is not.
- Leave a blank line after a Python docstring before executable code.
- Separate every multi-line Python or TypeScript statement or expression from the statement above it and the statement below it with a blank line. This is mandatory, not a preference, and applies at module level, in class bodies, and in function bodies; the only exemptions are the first statement of a block, the last statement of a block, and cases where a tool owns the layout: an import block is the standing example, because Ruff's import rules reject a blank line inside a group.
- Follow every Python or TypeScript statement that binds a newly constructed object or value with a blank line, unless the immediately following statement is also such a binding. Consecutive bindings are exempt and stay valid when adjacent, which is why runs of Django settings constants need no separation; statements that merely operate on an already-bound object, such as method calls, attribute mutations, and registrations, may also sit on consecutive lines, because they are executions against an object that already exists. This applies at module level, in class bodies, and in function bodies, and the TypeScript binding forms are `const`, `let`, and `var` declarations, including `new Foo()` and factory calls. When the binding itself spans multiple physical lines the multi-line rule above already demands blank lines on both sides and this rule adds nothing, and where the formatter forces a different layout the formatter wins.
- Leave a blank line above `return` when executable logic precedes it.
- Avoid routine inline explanatory comments. Prefer better naming, extraction, numpydoc/TSDoc documentation, and explicit abstractions. Allow comments only for constraints, invariants, or workarounds that structure cannot express clearly.
- Document every backend and frontend test with exactly three lines, in this order and nothing else: a `GIVEN ...` line, a `WHEN ...` line, and a `THEN ...` line, beginning on the line after the opening delimiter as every docstring does. No summary line, no blank line inside, no numpydoc sections, no TSDoc tags, no extra prose. Non-test callables in the test tree, such as fixtures, factories, helpers, and stubs, keep ordinary concise numpydoc/TSDoc documentation.
- Ruff is the Python formatter, linter, and import-order authority, including isort-compatible rules. Exclude Django-generated `**/migrations/**` from Ruff formatting/linting. Do not add standalone isort or Black without an explicit project-wide decision.
- Pyright is mandatory for Python static type checking. Exclude Django-generated `**/migrations/**` from Pyright analysis.
- Mark a deliberately unused Python parameter with an underscore prefix that keeps its meaning, such as `*_args`, `**_kwargs`, or `_payload`. Never use a bare `_`: two unused parameters in one signature would be a duplicate-argument `SyntaxError`, and the prefixed name keeps the signature self-documenting. Ruff's `ARG` rules are enabled so this is a CI gate rather than an editor preference.
- Never rename a parameter a caller passes by keyword or a framework introspects. Two cases are proven in this codebase: `override` in the dotenv interceptor is keyword-only and renaming it raises `TypeError`, and a Django Ninja handler's `request` cannot be prefixed because Ninja builds a Pydantic model from the signature and Pydantic raises `NameError: Fields must not use names with leading underscores`. Prefer consuming the parameter where that adds real value: the Django Ninja health handler logs the probing client at debug level, which is why no `ARG001` exemption exists anywhere in `pyproject.toml`. Only when a parameter genuinely cannot be used, exempt the file's role in `per-file-ignores`.
- Loguru is the single log sink for every backend process, installed through `LOGGING_CONFIG = "config.logging.configure"` and a `logging.Handler` that intercepts standard-library records. Application code keeps calling `logging.getLogger(__name__)` and must never import `loguru` directly, so Django, Celery, and third-party libraries all land in the same sink and the sink stays replaceable. `config/celery.py` connects an empty receiver to Celery's `setup_logging` signal so Celery cannot install its own format.
- Local logging is human-readable at `DEBUG` with Loguru `diagnose` enabled; `preproduction` and `production` emit serialized JSON, keep `diagnose` disabled because it prints surrounding variable values, and clamp the level so a `DJANGO_LOG_LEVEL=DEBUG` in the environment can never leak debug records. `config.logging.deployed_log_level` enforces that clamp and is covered by tests.
- Taplo is the TOML formatting authority for every TOML file in the repository, pinned in the backend `lint` dependency group and configured by the root `.taplo.toml`. Run it from the repository root with `uv run --project backend taplo fmt --check --diff`, keep `array_auto_collapse = false` so multi-line arrays stay expanded, and keep its indentation aligned with the `[*.{yml,yaml,toml}]` rule in `.editorconfig`. Taplo is the same engine the Even Better TOML editor extension uses, so editor-on-save formatting and the CI gate must not diverge.
- Express a lint suppression that follows from a file's role in Ruff `per-file-ignores`, not as an inline `# noqa`. Layered settings modules inherit shared configuration through `from config.settings.base import *`, so `F403` and `F405` are ignored for `config/settings/{local,preproduction,production,test}.py` in `pyproject.toml`. Keep each pattern as narrow as the role it describes, and prefer removing the cause over suppressing the finding: project-authored Python currently carries zero inline suppressions.
- Never source a secret from a literal in project-authored code, tests and test settings included. Read it from the environment and fall back to `django.core.management.utils.get_random_secret_key()` where a value must always exist. Generate local values with `openssl rand -base64 48` into a gitignored `.env.local`; `.env.example` keeps documented placeholders only.
- Organize every ignore file, including `.gitignore`, `.dockerignore`, and `.prettierignore`, plus every `.env` file, as comment-titled groups of related entries, with the entries inside each group sorted lexicographically. Group order carries meaning and is not alphabetized. One exception is mandatory in ignore files: a negation such as `!.env.example` must stay after the pattern it re-includes, because `!` sorts before `.` and a naive sort would silently make the negated file ignored again. Verify a reordering with `git check-ignore` for ignore files and `docker compose config` for `.env` files, never by eye.
- Use pytest with pytest-django is the mandatory backend testing stack. Keep backend tests in a top-level `tests/` directory at the same level as Django `manage.py`; do not colocate tests inside functional Django apps.
- Vitest is the mandatory frontend test runner, with React Testing Library for React component behavior tests. Keep frontend tests under first-level `src/tests/`; do not colocate test/spec files beside functional source modules.
- React Doctor is a frontend development-quality diagnostic and belongs in `devDependencies`. Run it against changed React/Next.js application code before frontend work is considered complete. Use the project-pinned version resolved through `bun.lock`, never an unpinned `@latest` invocation in CI. Treat findings as engineering signals and do not introduce unnecessary abstractions solely to satisfy a diagnostic.
- TypeScript documentation follows TSDoc: `https://tsdoc.org/`.
- Prettier is the frontend formatting authority for project-authored frontend code. Exclude `src/components/ui/**` (shadcn/ui-generated primitives) from Prettier formatting/checks.
- Use `prettier-plugin-tailwindcss` for Tailwind's canonical class order.
- Use `@trivago/prettier-plugin-sort-imports` for deterministic frontend import sorting unless an explicit project decision replaces it.
- Use pragmatic design patterns and hexagonal/vertical-slice boundaries; reject empty layers, generic repositories, needless interfaces/factories, or abstraction for its own sake.
- Backend persistence uses repositories/query modules where they create a meaningful boundary. Django ORM remains the implementation.
- Prefer Next.js Server Components, native `fetch`, caching, and revalidation for remote data. Add a client-side server-state library only after an explicit project decision driven by a concrete requirement.
- Docker is required for runnable services; Docker Compose is the local orchestration baseline.
- Run a container that writes into a bind mount as an unprivileged user matching the developer, not as root, and do not put a named volume on a path the host also writes. Docker creates a named-volume mountpoint on the host as root, so `frontend/.next` has no volume and the `web` service runs as the image's `bun` user, uid 1000; otherwise the first `docker compose up` on a fresh clone leaves that directory root-owned and every host `bun run` command fails with `EACCES`. A `node_modules` volume is still correct, because the container's Linux install must not shadow the host one.
- CI and Docker workflows must use committed `bun.lock` and `uv.lock` files and reproducible/frozen dependency installation where applicable. Production builds/installations must preserve runtime/dev dependency separation rather than installing all developer tooling by default.
- Support configuration separation for `local`, `preproduction`, and `production`; only `local` needs to run during MVP development. Keep a single committed `.env.example`: the variable names are identical across environments and `DJANGO_SETTINGS_MODULE` selects the environment, so per-environment template files would duplicate the contract and drift. Do not add `.env.preproduction.example` or `.env.production.example`. The local file is `.env.local` and `--env-file` is the only environment selector, so every `docker compose` command carries it.
- Declare in `compose.yml` exactly which variables each service receives, never `env_file:` with a whole file. This keeps one selection mechanism, so `--env-file` moves every service at once, and it keeps least privilege readable: `web` must never receive `SPORTMONKS_API_TOKEN` or `POSTGRES_PASSWORD`. Declare each variable as `${NAME?hint}` without a colon, which fails fast on an absent variable while still accepting a legitimately empty one such as `SPORTMONKS_API_TOKEN=`.
- Never expose Sportmonks credentials to client-side code and never call Sportmonks directly from the browser.
- Preserve provider/domain separation; never leak raw Sportmonks contracts or provider type IDs into public APIs or UI.
- The active Sportmonks Starter subscription has five leagues, 2,000 API calls per entity per hour, and the Odds & Predictions add-on. MVP league scope: Premier League (`8`), Bundesliga (`82`), Ligue 1 (`301`), Serie A (`384`), and La Liga (`564`).
- Treat prediction availability as fixture-dependent and model an unavailable state when Sportmonks does not provide predictions.
- All critical background and synchronization jobs must be idempotent and retry-safe.
- CI tests must not rely on live Sportmonks calls.
- GitHub Actions must eventually enforce Ruff, Pyright, pytest/pytest-django, Prettier, TypeScript, Vitest, relevant React Testing Library tests, React Doctor for changed React/Next.js code, branch-name validation, commit-message validation, and relevant build/test gates.
- Commit messages follow `https://gist.github.com/qoomon/5dfcdf8eec66a051ecd85625518cfd13`.
- Commit descriptions use imperative present tense, lowercase initial text, and no trailing period.
- Branch names follow Conventional Branch 1.1.0: `https://conventionalbranch.org/`.
- Prefer purpose branches such as `feature/<description>`, `fix/<description>`, `hotfix/<description>`, `release/<description>`, and `chore/<description>`.
- Django migrations are generated artifacts: keep them versioned and review their operations/schema impact, but exclude `**/migrations/**` from Ruff formatting/linting and Pyright analysis. Database migrations must be backward-safe when practical and included in the PR that requires them.
- No destructive production-data operation without explicit human approval.
- No secrets, tokens, `.env.*` files other than the tracked `.env.example`, or real user/provider data in commits, logs, fixtures, screenshots, issues, or PR descriptions.
- Do not merge or recommend merging with failing tests, type checks, lint/format checks, or unresolved critical findings.
